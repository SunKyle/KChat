# KChat 业务架构文档

> 生成日期：2026-06-27 | 分支：main

## 一、产品定位与价值主张

### 1.1 产品身份

KChat 是一个**多模型 AI 聊天桌面工作站**。用户在一个统一界面中与 OpenAI、Anthropic、Google、Ollama、Azure 等多种 AI 提供商对话，不用在多个工具之间跳转。

### 1.2 目标用户

面向所有需要 AI 辅助的通用用户——**开发者、写作者、研究者、学习者**。他们通常在桌面端使用，日常工作需要频繁切换不同 AI 模型，并且需要对话历史管理和长期记忆来保持上下文连续性。

### 1.3 核心任务（用户视角）

| 任务 | 说明 |
|------|------|
| 多模型对话 | 与不同提供商的 AI 模型进行流式对话，自由切换模型 |
| 对话管理 | 创建、浏览、搜索、删除历史对话，保持工作有序 |
| 跨会话记忆 | 系统自动记住用户偏好、技能、项目等，下次对话自动带入 |
| 行动捕捉 | 从对话中将关键信息转化为笔记和待办事项 |

### 1.4 产品原则

1. **少即是多** — 每个界面只做一件事。功能通过层级和时机呈现，而非堆砌。
2. **内容优先** — 对话是核心。所有 UI chrome 服务于对话，不争夺焦点。
3. **流动感** — 操作之间平滑过渡，状态切换有自然的中间态。
4. **静默聪明** — 长期记忆、模型切换等智能功能在后台工作，不需要用户额外操作就能受益。
5. **尊重注意力** — 通知、状态变化、动画都不应打断用户思维流。

### 1.5 不做的事

- 不是花哨/繁杂的"全能工具" — 克制大于表现
- 不是典型的国内工具风格 — 避免过度装饰、信息密度过高
- 不是企业软件 — 避免僵硬的表单和功能堆砌
- 不是"炫技"产品 — 功能服务于任务，不喧宾夺主

## 二、业务领域模型

### 2.1 核心领域实体

```
用户 (User)
 ├── 身份: userId (默认 "default")
 ├── 资料: nickname, avatar, email, bio
 ├── 偏好: theme (dark/light), language (zh-CN/en/ja/...), notification settings
 ├── 隐私: onlineStatus, messageHistory, readReceipts, typingIndicator
 └── 设置: defaultModel, memoryEnable, contextSize, autoTitle
```

| 实体 | 业务含义 | 生命周期 |
|------|---------|---------|
| **UserProfile** | 用户的公开资料和个性化配置 | 创建后持续更新，与 userId 1:1 |
| **UserSetting** | 用户的系统级行为偏好 | 创建后持续更新，与 userId 1:1 |
| **Conversation** | 一次对话会话 | 创建 → 消息积累 → 可能被删除/归档 |
| **Message** | 对话中的单条消息（用户或AI） | 随对话产生，级联于对话删除 |
| **LongTermMemory** | 从对话中提取的持久化知识片段 | 自动/手动提取 → 过期或手动删除 |
| **ModelConfig** | 用户配置的外部 AI 模型连接 | 创建 → 启用/禁用 → 删除 |
| **Note** | 用户笔记（可从对话总结生成） | 创建 → 编辑 → 可关联记忆 |
| **Todo** | 用户待办事项（可从对话识别） | 创建 → 状态流转 → 完成/删除 |
| **APIKey** | 用户自行管理的 API 密钥 | 创建 → 使用 → 删除 |
| **PromptTemplate** | 系统提示词模板（版本化） | 创建 → 更新升级版本 → 启用/禁用 |

### 2.2 实体关系图（业务视角）

### 3.1 对话引擎

对话引擎是 KChat 的核心——所有其他能力都围绕对话展开。

**同步对话**：用户发送消息 → 系统完整处理后返回结果。适用于短回答、非流式场景。

**流式对话**：用户发送消息 → 系统通过 SSE (Server-Sent Events) 逐字推送回复。这是主要交互模式，提供打字机效果的实时体验。

**模型选择策略**：
- 默认从 Ollama 本地模型列表加载（`/api/tags`）
- 叠加用户自定义的云端模型配置（`ModelConfig`，格式：`配置名:模型ID`）
- 支持按 `TEXT`/`IMAGE` 分类过滤
- 请求中指定 model → 服务端根据命名约定自动路由到对应客户端

**联网搜索**：对话时可选择开启网络搜索，搜索结果作为附加上下文注入 Prompt，带时间戳。当前支持 Bing 引擎。

**图像生成**：支持两种路径——
- OpenAI 兼容的图像 API（DALL-E 风格，`/v1/images/generations`）
- Stable Diffusion WebUI API（`sdapi/v1/txt2img` 或 `sdapi/v1/img2img`）

**显示形式**：生成的图像以 Markdown `![Generated Image](url)` 格式通过 SSE 流式推送到前端。

### 3.2 记忆系统

记忆系统是 KChat 区别于普通聊天工具的核心竞争力——让 AI "记住"用户。

#### 短期记忆（对话上下文）

```
目的：让 AI 在当前对话中记住最近的交流内容
机制：缓存最近 20 条消息（用户 + AI 交替），随对话推进滚动更新
存储：内存（L1，ConcurrentHashMap）→ Redis（L2，24h 过期）双层缓存
触发：每次对话自动维护，无需用户干预
```

#### 长期记忆（跨会话知识）

```
目的：跨对话记住用户的重要信息（身份、偏好、项目、技能等）
机制：
  1. 语义检索：用户每次发消息时，用当前消息内容做向量相似度搜索
  2. 召回 top-5 相关记忆，按重要性降序注入 System Prompt
  3. 让 AI "知道"用户的背景信息，无需用户重复说明

记忆类型（11 种）：
  PROFILE     — 用户身份、职业、角色
  PREFERENCE  — 偏好、喜好、习惯
  PROJECT     — 正在进行的项目
  SKILL       — 技能、技术栈
  TASK        — 任务、目标
  KNOWLEDGE   — 知识领域
  RELATION    — 人际关系
  EVENT       — 事件、活动
  RULE        — 规则约束
  FACT        — 事实信息
  EXPERIENCE  — 经验经历
```

#### 自动记忆提取

```
触发条件（可配置）：
  - 对话消息数达到阈值（默认 5 条）
  - 空闲超时（默认 5 分钟，定时扫描待实现）

提取流程：
  1. 将最近 N 条消息（上下文窗口，默认 20 条）发送给 LLM
  2. LLM 按结构化 Prompt 提取事实并评估类型/重要性/置信度
  3. 过滤：低于置信度阈值（默认 50%）→ 丢弃
  4. 过滤：低于重要性阈值（默认 4/10）→ 丢弃
  5. 去重：与已有记忆比较（内容归一化后精确匹配）
  6. 入库：数据库 + 向量索引双写

降级策略：
  LLM 调用失败时，回退到关键词规则提取（正则匹配身份/技能/偏好/项目/任务等模式）
```

### 3.3 知识管理（笔记 + 待办）

对话中产生的有价值信息，可以沉淀为笔记和待办——这是从"聊"到"做"的行动闭环。

**笔记 (Note)**：
- Markdown 格式，支持分类和标签
- 可通过"对话总结"功能：选中 AI 回复 → 一键生成结构化的 Markdown 笔记（LLM 提取标题 + 整理正文）
- 支持置顶、搜索、按分类筛选
- 可关联到记忆 ID（`memoryId` 字段）

**待办 (Todo)**：
- 支持状态流转：`pending` ↔ `completed`
- 支持优先级（high/medium/low）和截止日期
- 支持搜索、按状态/优先级筛选、过期待办提醒
- 完成时自动记录 `completedAt` 时间戳

**缓存策略**：笔记和待办列表使用 `CacheService` 做应用层缓存，写操作后主动失效。

### 3.4 用户中心

**资料管理**：昵称、头像、邮箱、个人简介

**偏好设置**：
- 主题（dark/light）
- 语言偏好（zh-CN/en/ja/ko/fr/de/es/ru）—— 系统用自然语言名（如"中文（简体）"）注入 System Prompt，让 AI 以用户语言回复
- 通知偏好（消息/邮件/推送/声音，四维独立开关）

**隐私控制**：
- 在线状态可见性
- 消息历史保留
- 已读回执
- 输入状态指示器

**API Key 管理**：用户自行创建/管理 API 密钥，用于调用外部模型服务

**设备管理**：记录登录设备（类型、IP、位置、最后活跃时间），支持远程删除

### 4.2 记忆自动提取流程

```
对话进行中...
    │
    ├── 每条消息 → Counter.increment(conversationId)
    │
    ▼
count < 阈值 (5)  →  继续等待
    │
    ▼
count >= 阈值 (5)  →  触发提取
    │
    ├── Counter.reset()  （重置计数器）
    │
    ▼
获取最近 20 条消息  →  发送给 LLM
    │
    ├── 成功  →  解析 JSON {summary, memories[{content, type, importance, confidence}]}
    │            │
    │            ├── 过滤 1：confidence < 0.5 → 丢弃
    │            ├── 过滤 2：importance < 4   → 丢弃
    │            ├── 过滤 3：内容已存在        → 丢弃
    │            │
    │            ▼
    │         批量保存（数据库 + 向量索引）
    │
    └── 失败  →  降级：规则提取（关键词匹配）
                 │
                 ├── 检测 "使用...开发" → SKILL
                 ├── 检测 "我是/我叫"  → PROFILE
                 ├── 检测 "喜欢/偏好"  → PREFERENCE
                 ├── 检测 "项目/开发"     → PROJECT
                 ├── 检测 "需要/必须"  → TASK
                 ├── 检测 "明天/计划"  → EVENT
                 ├── 检测 "朋友/同事"  → RELATION
                 └── 检测 "熟悉/掌握"  → KNOWLEDGE
```

### 4.3 对话总结流程

```
用户选中 AI 回复 → 点击"总结为笔记"
    │
    ▼
构建专用 System Prompt（含语言偏好指令）
    │
    ├── 要求 LLM 输出格式：
    │   标题（不超 50 字，纯文本，首行）
    │   ---（分隔线）
    │   正文（结构化 Markdown）
    │
    ▼
模型路由（同对话）
    │
    ▼
解析响应：按 "---" 分隔提取标题和正文
    │
    ▼
返回 {title, summary}  →  前端新建笔记
```

### 4.4 重新生成流程

```
用户在历史对话中选中某条 AI 消息 → 点击"重新生成"
    │
    ▼
查找该 AI 消息之前最近的用户消息（precedingUserMessage）
    │
    ▼
事务操作：
  1. 删除该 AI 消息之后的所有消息（对话分支裁剪）
  2. 清除短期记忆缓存（强制从 DB 重新加载）
    │
    ▼
重新执行完整对话流程：
  召回记忆 → 组装 Prompt → 调用 LLM → 更新记忆 → 持久化
    │
    ▼
覆盖原 AI 消息内容 + 更新时间戳
```

### 4.5 模型配置的生命周期

```
用户进入设置 → 模型配置 → 添加新模型
    │
    ▼
填写：名称 + 模型ID + Base URL + API Key + 类型 + 分类
    │
    ├── 校验：API Key 非空
    ├── 校验：名称+模型ID 组合唯一
    │
    ▼
创建配置（enabled = true）
    │
    ▼
模型列表刷新：Ollama 本地模型 + 所有 enabled 的自定义模型
    │
    ├── 自定义模型显示为 "配置名:模型ID" 格式
    ├── 对话中选择该模型 → 解析出配置名 → 获取 baseUrl + apiKey → 路由到 OpenAICompatibleClient
    │
    ▼
用户可随时编辑/禁用/删除配置
```

## 五、业务规则汇总

### 5.1 对话规则

| 规则 | 值 | 说明 |
|------|-----|------|
| 新对话默认标题 | "新对话" | 首次收到消息后触发 AI 自动生成标题 |
| 自动标题触发条件 | 标题为"新对话" + 用户启用了 autoTitle | 仅在首条消息后触发一次 |
| 短期记忆窗口大小 | 20 条消息 | 超过后滚动替换 |
| 短期记忆过期时间 | 24 小时 | Redis TTL，内存随应用重启清空 |
| 重新生成的约束 | 只能重新生成 AI 消息 | 自动找到前置用户消息作为输入 |

### 5.2 记忆规则

| 规则 | 默认值 | 说明 |
|------|--------|------|
| 提取触发消息数 | 5 条 | 对话中每累计 N 条用户+AI 消息触发一次提取 |
| 最低置信度 | 50% | LLM 返回的 confidence < 0.5 的记忆丢弃 |
| 最低重要性 | 4/10 | importance < 4 的记忆丢弃 |
| 语义召回数 top-K | 5 条 | 每次对话注入的长期记忆上限 |
| 向量相似度阈值 | 0.3 | 余弦相似度低于此值的记忆不召回 |
| 向量维度 | 384 | 当前使用确定性伪嵌入，非真实语义 |
| 长期记忆召回过滤 | 重要性 ≥ 3 | 低于此阈值的记忆即使相似度高也不召回 |

### 5.3 输入安全规则

| 规则 | 值 | 说明 |
|------|-----|------|
| 最大输入长度 | 4096 字符 | 超出返回错误 |
| 最小输入长度 | 1 字符 | 空输入返回错误 |
| 注入检测模式 | 11 种 | {{}}、{% %}、`<script>`、SQL DROP/DELETE/UNION 等 |
| 敏感信息模式 | 12 种 | 手机/身份证/邮箱/银行卡/护照/车牌/IP/微信/QQ/邮编/URL/IPv6 |
| 脱敏方式 | `***` 替换 | 同时作用于输入内容和日志输出 |

### 5.4 限流规则

| 规则 | 值 | 说明 |
|------|-----|------|
| 限流算法 | Redis 有序集合滑动窗口 | 1 分钟窗口 |
| 请求上限 | 10 次/分钟 | 可配置 |
| 限流范围 | 当前仅内容优化接口 | 通过 `@RateLimited` 注解控制 |
| 超限响应 | HTTP 429 + retry-after | 自动推算最早的请求过期时间 |

### 5.5 提示词规则

| 规则 | 值 | 说明 |
|------|-----|------|
| 默认 Token 上限 | 8192 | 超出时触发智能截断 |
| 截断优先级 | SystemMessage > 当前用户输入 > 最近对话 | 从后往前保留历史 |
| 语言指令 | "请使用 {语言名} 回复。" | 无偏好时不注入 |
| 模板占位符 | `{language_clause}`, `{long_term_memory}` | 从 DB 模板或硬编码模板中替换 |
| 网络搜索结果格式 | `- [标题](URL): 摘要` | 附当前时间戳（上海时区） |
| 总结 Prompt 格式 | 标题 + `---` + 正文 | 多语言支持（10 种语言映射） |

## 八、业务演进方向（基于当前代码分析）

当前系统已实现核心对话和记忆闭环，以下为自然演进方向：

1. **真实语义嵌入**：当前向量嵌入为确定性哈希伪嵌入，替换为真实 Embedding API（如 Ollama embedding 模型）可显著提升记忆召回质量。
2. **用户认证体系**：当前通过 `userId` 查询参数识别用户。引入 JWT 认证可实现真正的多用户安全隔离。
3. **对话分支**：当前重新生成采用"覆盖"模式（删除后续消息）。可扩展为对话树/分支，支持探索多条回复路径。
4. **记忆冲突检测与更新**：当前记忆提取只做新增+去重。可扩展为：新记忆与旧记忆矛盾时提示用户确认，或自动更新。
5. **记忆过期策略完善**：当前仅清理数据库中的过期记忆，向量索引未同步。需实现全链路过期清理。
6. **多设备实时同步**：当前短期记忆与 Redis 绑定。可通过 Redis Pub/Sub 实现多设备消息同步。
7. **Prompt 模板市场**：当前模板系统支持版本化和动态加载。可扩展为社区模板分享。
